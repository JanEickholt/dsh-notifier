## 一、P1

### G-01 · 钉钉 Stream ack 回执三重偏差

- **定位**：`src/inbound/dingtalk-stream.mjs:219-227,307` —— `ackFrame(String(frame.messageId))` 读顶层 messageId；回执头用 `requestId` 字段名；data 未字符串化且缺 `message:'OK'`
- **易错辨析**：三处偏差叠加（读错路径 + 头字段名错 + 载荷形状错），单看每一处都"像个能跑的帧"，只有对照官方 `client.mjs` 才能确认服务端全不认。最容易看漏的是头字段名：官方回执头就是 `messageId`，不是 restful 惯用的 `requestId`——直觉写法恰好是错的。测试 mock（`test/inbound.dingtalk.test.mjs:153-156,295`）把顶层 messageId 形态钉死成契约，是 1352 测试全绿仍漏检的直接原因
- **竞品参照**：dsh-im 直接用 `dingtalk-stream` 官方 SDK，ack 帧构造在 SDK `client.mjs` 内，无此问题——凡官方 SDK 覆盖的协议点，竞品零成本继承正确性

### G-02 · 钉钉 SYSTEM/ping 探活帧零应答，SYSTEM 帧族整体未处理

- **定位**：`src/inbound/dingtalk-stream.mjs:303-316` —— `handleFrame` 无 `frame.type==='SYSTEM'` 分支，ping/disconnect/KEEPALIVE/REGISTERED 全部落入业务消息路径后静默丢弃
- **易错辨析**：极易误判为"WS 协议层 ping/pong 自动处理了，不用管"——但官方 SDK 对 SYSTEM ping 是应用层回显帧（headers+data 原样返回，data 含必须回显的 opaque），与传输层心跳是两码事。漏答的表现是周期性掉线重连，日志只有"重连"没有根因，排障方向容易被带偏到网络层。与 G-01 是同根：裸协议实现丢掉的都是 SDK 隐式处理的协议点
- **竞品参照**：同 G-01，官方 SDK `WSClient` 内置 ping 应答与 SYSTEM 事件分发

### G-03 · 微信 iLink 发送按 UTF-16 码元切块，emoji/生僻字被切半

- **定位**：`src/channels/wechat-ilink/legacy-core.mjs:374-386` —— `for (i += size) content.slice(i, i+size)` 按码元切；同款问题 `src/inbound/qq-gw.mjs:422,460` 两处
- **易错辨析**：JS 字符串 length/slice 全是 UTF-16 语义，纯中文测试永远测不出（BMP 内字符 1 码元=1 码点），必须 emoji（星体平面）跨块边界才炸——切出孤立代理项后微信端显示乱码或拒收。最讽刺的辨析点：`src/inbound/segment.mjs` 里码点安全分段已存在（`Array.from`），Telegram 侧也有同款代理对保护，唯独微信发送路径没复用——不是不会写，是没意识到这里是同一个问题
- **竞品参照**：dsh-im 的 `safeSliceIndex`（切点落在代理对回退一位）正是此问题的标准解法，说明竞品真机踩过此坑

### G-04 · `/stop 任意文字` 被误判为取消命令

- **定位**：`src/inbound/conversation.mjs:521-525` —— `trimmed === '/stop' || trimmed.startsWith('/stop ')` 前缀匹配即取消
- **易错辨析**：典型的前缀命令匹配陷阱：`/stop 一下别急`、`/stop 等等再发` 误触发 `agent.cancel()`，且参数静默忽略、无确认无回滚——用户一句话把长任务杀了。I 轮终审修正：`/stopwatch` 不中招（`startsWith('/stop ')` 要求命令后紧跟空格）——审查此前缀时容易同时高估与低估其杀伤面，真正命中的是"精确 `/stop`"与"`/stop `+任意尾巴"两种形态
- **竞品参照**：dsh-im 命令集更小（无 /stop 类高危命令），此坑未踩；其命令解析全部精确匹配

### G-05 · 管理台 settleQuestion 审计写失败把成功裁决变成 500

- **定位**：`src/admin/api.mjs:1204-1253` —— `adminSettle` 裁决生效后 `appendAudit` 在 try 块外执行，磁盘满/权限异常直接抛 500
- **易错辨析**：业务状态与可观测性副作用的顺序问题——裁决已生效但响应报错，前端引导用户重试，重试命中 already-resolved 再报错，内外状态认知分叉。易错点：审计"只是记日志"的直觉让人把它留在主 try 里，恰恰忘了它有 IO 就会抛
- **竞品参照**：dsh-im 无管理台裁决面，不存在对应路径

### G-06 · 命令解析不支持 `/cmd@botname` 变体

- **定位**：`src/inbound/commands.mjs:25-31` —— `parts[0].slice(1)` 不剥 `@botname` 后缀；TG/钉钉入站也无 @ 剥离
- **易错辨析**：Telegram 群聊客户端自动补全 `/cmd@mybot` 是平台标准行为，单聊测试永远复现不了——群聊里 `/whoami` 全部变成普通消息进 agent。易错点：命令解析单元测试都是理想形态输入，真实平台输入的形态差异只有真机群聊才见
- **竞品参照**：dsh-im 主要做单聊桥接 + 官方 SDK（SDK 的 command handler 自带 @ 剥离），未显式处理也不踩坑

## 二、P2

### G-07 · QQ 网关关闭码无语义处理 + token 永不主动失效

- **定位**：`src/inbound/qq-gw.mjs:404-407` —— close 一律 resume+退避不看 code；全文件无 `tokens.invalidate()` 调用
- **易错辨析**：`invalidate()` 在 `_tokens.mjs` 里存在且正确，但 QQ 网关侧从未调用——token 被平台提前吊销（close code 4004）时，带着同一缓存 token 无限重连直到 TTL 自然过期。易错点：重连逻辑本身是对的（RESUME/退避都对），"重连正确但带着死凭证重连"这个组合只有对着官方 SDK 的关闭码分支表才能看出来。官方 SDK 语义：4004 刷 token、4008 固定等 60s（限流码走短退避反而雪崩）、4006/4007/4009 弃会话重 IDENTIFY
- **竞品参照**：dsh-im 用 `qqbot-connector` SDK，reconnect.ts 的关闭码分支表全量继承

### G-08 · Telegram 429 不读 retry_after

- **定位**：`src/inbound/telegram-bot.mjs` `api()` 错误路径——grep `429|retry_after` 零命中
- **易错辨析**：TG 的 429 响应带 `parameters.retry_after`（秒），固定短退避在限流期是连续撞墙。易错点：退避机制存在（`errorBackoffMs` 默认 5s）给人"已处理限流"的错觉，但 5s 与平台要求的 N 秒不匹配时越撞越死
- **竞品参照**：dsh-im 用 grammY/telegraf 系 SDK，框架内置 flood control（429 自动等待）

### G-09 · Server酱 SC3（sctp 前缀 key）不支持

- **定位**：`src/adapters/serverchan.mjs:9,22` —— 固定 `sctapi.ftqq.com` Turbo 域名
- **易错辨析**：SC3 用户的 key 打 Turbo 端点直接 404，报错文案完全不提代际问题——用户第一反应是 key 错了去重置，越弄越乱。易错点：Turbo API 仍存活，配置校验全过，只有发送时 404，且 404 文案无代际提示
- **竞品参照**：dsh-im 按 key 前缀分流 sctp/ft07 域名，SC3 开箱可用

### G-10 · 钉钉建连 body 用 `uesrAgent`，官方 SDK 全系用 `ua`

- **定位**：`src/inbound/dingtalk-stream.mjs:201` + 头注释:9-10（"uesrAgent 是官方 SDK 的拼写错误字段名，服务端认的就是它"）
- **易错辨析**：本条是审查过程自我纠错的样本——终审报告曾采信注释判定"勿改"，后拉取 2.1.4/2.1.6-beta.1/2.1.7-beta.1 三个版本源码逐行核对：建连请求全部是 `ua: this.config.ua`，无任何版本存在 `uesrAgent`。注释的"官方拼写错误"说法查无实据。当前不致故障（建连靠 clientId/clientSecret 鉴权，未知字段大概率被忽略），但注释会误导后续维护者把错误字段名当协议事实传承
- **竞品参照**：dsh-im 官方 SDK 建连，字段名天然正确

### G-11 · `_tokens` invalidate 不清 inflight，旧任务晚完成把失效 token 写回缓存

- **定位**：`src/adapters/_tokens.mjs:17-35` —— `invalidate()` 只置 `cached=null`；在飞的旧 inflight IIFE 完成时无条件执行 `cached = {...}`，可能覆盖新 inflight 刚写入的新 token
- **易错辨析**：本条经 A 轮专项复核修正过一次描述——`get(force=true)` 并不 join 旧 inflight（`if (!force && inflight !== null)`），所以"重试拿到旧任务结果"的原表述不准。真实竞态是写回覆盖：token 被平台提前吊销（钉钉 errcode≠0 / 企微 40014）→ invalidate → 新 inflight 取新 token → 此前在飞的旧 inflight（吊销前发起，拿到的正是被吊销的 token）晚一步完成 → 把坏 token 连同 `expiresAt=now+7200s` 写回 cached → 理论上此后两小时都用死 token。触发窗口极窄（需要 invalidate 前一瞬恰有 get 在飞且完成更慢），但后果与窗口不成比例。钉钉 `postJsonWithToken` 的"作废重取重试一次"能当场自愈，真正受伤的是同一 manager 的后续调用方
- **竞品参照**：dsh-im 各官方 SDK 自带 token 缓存（SDK 内部有 generation/版本号防写回竞态）

### G-12 · 微信 iLink 轮询假死无应用层检测

- **定位**：`src/channels/wechat-ilink/legacy-core.mjs:273-325` —— 轮询循环自管失败计数，无"连续零消息超时"监督
- **易错辨析**：TCP 活着但服务端不再推消息的假死，现有熔断（只覆盖 sendmessage 限流）和失败计数（只覆盖显式异常）都不触发——通道静默失效，用户以为插件挂了。易错点：有重连有退避有熔断的代码看起来"韧性完备"，三类保护保护的都不是这个故障模式
- **竞品参照**：dsh-im 有通用 supervisor（15s 对账 + 退避序列 + 防重入），假死可检测

### G-13 · 渠道枚举 4 份硬编码

- **定位**：`src/admin/api.mjs:35`、`src/inbound/identity.mjs:19`、`src/inbound/target-guard.mjs`、`src/assembly/inbound-channels.mjs:19-26` —— 同一"支持哪些入站渠道"事实 4 份运行时拷贝
- **易错辨析**：新增通道漏改任何一处，症状各不相同（admin 422 / 绑定静默无效 / 形态守卫 fail-open），没有一个报错指向"枚举不同步"——排查时极易当成新通道自身的 bug。这是横切常量的经典散落问题
- **竞品参照**：dsh-im 渠道面窄且用 SDK 常量，未形成此债

### G-14 · 出站配置"视图热、投递冷"

- **定位**：`src/admin/api.mjs:899-924`（putChannel 只写 store）+ `src/index.mjs:203,618-662`（投递层持装配时快照）
- **易错辨析**：管理台保存后 UI 即时回显新配置，但 notifier 到重启才用——"改了没生效"与"改了生效了"两种体验在同屏并存（对照组成员/绑定写后半秒热生效）。易错点：不是 bug 而是语义分裂，但 UI 无任何"待重启"标记，用户无法区分
- **竞品参照**：dsh-im 配置变更走全量重建（牺牲瞬断换一致性），不存在双速语义

### G-15 · bus 消息消费优先级 = 装配注册顺序

- **定位**：`src/inbound/bus.mjs:173-180` + `src/questions/router.mjs:788-789` 注释（"审批编号回复 > 提问编号回复 > 普通对话"仅存于注释）
- **易错辨析**：核心优先级契约完全由 `index.mjs` 装配顺序 + 注释维系，重排装配块不报任何错，「1」的归属静默改变。易错点：这是"约定优于配置"的暗契约，测试若按现装配顺序写 mock 也测不出来
- **竞品参照**：不适用（dsh-im 无审批/提问双链争抢问题）

### G-16 · 审批 waiter 纯内存，与持久化 ledger 生命周期可分叉

- **定位**：`src/inbound/bus.mjs`（waiters Map 仅内存）+ store ledger（`ap:` 前缀行跨重启存活）
- **易错辨析**：热重载/崩溃重启后 pending 账本行还在而 waiter 已死，用户点旧卡片收到「已处理」误导回执，宿主侧等待的审批 promise 永远等不到答案（直到自身超时）。易错点：两边各自看都"正确"（账本持久化对、waiter 内存态对），分叉只在生命周期边界出现
- **竞品参照**：不适用（竞品无远程审批）

### G-17 · Telegram/飞书旧卡片兼容放行窗口

- **定位**：`src/inbound/telegram-bot.mjs:240-257`（refs TTL 15min 兜底）、`src/inbound/feishu-bot.mjs:379-395`（无等价 TTL 约束）
- **易错辨析**：升级前在途卡片缺来源会话元数据，warn 后放行——TG 有 refs TTL 兜底，飞书侧没有，同一策略两渠道强度不同。窗口内卡片被转发后点击可跨会话裁决。易错点：这是兼容性让步，有 warn 有理由，但强度不对称容易被当成"飞书也受了保护"
- **竞品参照**：不适用（竞品无按钮卡片裁决）

### G-18 · 事件去重键 `session.id:event.seq` 吞掉宿主重放

- **定位**：`src/event-listener.mjs:426-427` —— dedup 对所有 intent 生效（含 approval/asked 即时推送）
- **易错辨析**：宿主重放同 seq 事件时，第二次真实需要的审批提醒被静默吞掉。易错点：去重键对"每 turn 一条"类事件完美，对"同 seq 多负载"类事件（重放携带不同 payload）就错——键粒度对不同事件类型的适配性差异容易被一个统一键掩盖
- **竞品参照**：不适用（竞品不订阅宿主事件流）

### G-19 · `selectHostEventContext` 猜测根上下文（C 轮加证）

- **定位**：`src/host-events.mjs:42-48` —— scoped child 时主动切 root 订阅
- **易错辨析**：C 轮专项拿到了 cordis 源码级证据（`vendor/cordis/src/events.ts:165-175` 事件服务按 context filter 过滤 listener、`core/agent/src/runtime-types.ts:175` 声明 `agent/disposed` 为 Scoped 事件）：root 订阅对 scoped 事件可能漏收（通知闭环丢审批/报错提醒）或听到不该听的（隔离失效）。易错点："往 root 挂监听最稳"是直觉，恰好与 cordis 的 scoped 过滤机制相悖；插件侧靠 `payload.agent ?? payload` 的宽容解析部分掩盖了丢事件症状
- **竞品参照**：不适用（宿主生态内无同类插件可比）

### G-20 · `pairing.mint()` 双次落盘崩溃窗口

- **定位**：`src/inbound/pairing.mjs:205-241` —— 先落 minted → audit → 改 active 再落盘
- **易错辨析**：两写之间崩溃，盘上残留 minted 未下发的孤儿码（TTL 内仍可被兑换）。易错点：两次写各自原子，但"状态推进"整体非原子——单写原子性给了人事务完整的错觉
- **竞品参照**：不适用（竞品无配对码机制）

### G-50 · 出站超时盲目重试形成 at-least-once 重复通知（E~H 轮新增）

- **定位**：`src/routing.mjs:48-60,98-119`（timeSensitive `attempts:3` + 指数退避）+ `src/adapters/_shared.mjs:75-99`（`postJson` 超时统一抛 `TIMEOUT`，不区分"已送达未应答"）
- **易错辨析**：超时的三种真况——连接失败（重试安全）/ 服务端已收到但响应慢（重试=重复投递）/ 响应丢失（同前）——被折叠成第一种。分段部分成功已有 `noRetry` 短路（`notify.mjs:44-52`），说明作者意识到"重复轰炸"这个面，但"整条超时"这一支仍盲目重发；timeSensitive 默认 3 次尝试，用户最坏收 3 份同一通知。易错点：只有无幂等键的 HTTP 渠道受害——QQ 出站已用冻结 `msg_seq` 自愈（`qq-bot.mjs:65-89`），而钉钉/飞书/TG/webhook/企微全裸奔；且测试 mock 的 fetch 不会出现"超时但已送达"，1352 绿测结构上永远测不出
- **竞品参照**：dsh-im 文件投递把此类失败标 `uncertain: true` 并拒绝盲目重试（`feishu-channel.mjs:359-366`），错误体系显式区分"投递结果未知"与"确认失败"

### G-51 · 合并窗按 `channel:userId` 聚合，同用户跨 chat 消息串台合并（I 轮）

- **定位**：`src/inbound/conversation.mjs:475,477,566-591` —— pending 键与 flush 键均为 `${channel}:${userId}`，不含 chatId 维度；flush 采用最后一条消息的 envelope
- **易错辨析**：注释与键构造都写 `${channel}:${userId}`，把"用户"当成了聚合边界——但 envelope 还有 chatId：同一 Telegram 用户在私聊与群（或两个群）窗口内先后发言，全部并成一条，按最后一条的 chat 投递与回执。route() 拿 merged 文本走 resolveTarget，路由对了但内容已串台；"一人一窗"的单会话测试永远测不出，这是键粒度少一维的静默错聚合
- **竞品参照**：dsh-im 按平台消息原生 chat/会话对象隔离（SDK 事件对象自带 chat 维度），无跨会话合并面

### G-52 · 裸编号多选拒绝逗号后空格，答案被当普通文本投给 agent（J 轮）

- **定位**：`src/questions/router.mjs:705` —— `/^\d{1,2}([,，]\d{1,2})*$/` 不容 `1, 3`（逗号+空格）、`1、3`、`1 3`；不匹配即 `return false` 落回对话路由
- **易错辨析**：正则已兼容全角逗号却不容半角逗号后一个空格——恰是手机输入法最常见形态；被拒后不裁决、不提示，"1, 3" 作为普通消息进 agent 上下文（答案丢失+语境污染双害），用户以为已作答。测试只喂理想形态 `1,3`；单选场景掩盖多选解析面
- **竞品参照**：dsh-im `src/channels/shared/harness-question.mjs:70-81` 用 `split(/[,，、;；\n]+/)` 逐 token trim，多分隔符全兼容

### G-53 · 错误文案无"公开码/内部细节"分层，HTTP 状态、响应体、网络原文直达用户（J 轮）

- **定位**：`src/adapters/_shared.mjs:68,95,125,146,172`（`${channel}返回 HTTP ${status}`+200 字符响应体、`${channel}请求失败: ${error.message}`）+ `src/notify.mjs:89,154`（`failed[].error` 原样透传进事件/工具反馈）+ `src/health.mjs:27,37`（detail 直传 admin UI）

## 四、安全类

### S-01 · 结构性 · 插件全权限运行，权限声明无强制执行

- **定位**：宿主 `vendor/loader/src/internal.ts:1`（原生模块加载，无沙箱）+ 插件 `package.json:89-99`（dshWorkshop.permissions 仅声明性元数据）
- **易错辨析**：C 轮加证——宿主 loader 实际只读 `id/name/config`（`vendor/loader/src/config/entry.ts:9-16`），permissions 等字段运行时零消费：声明与执行完全脱钩。插件可任意读写文件、执行命令、外发数据，缓解只剩来源信任+锁版本+升级 diff 复审
- **竞品参照**：dsh-im 同宿主同模型，同等暴露

### S-02 · 中危 · webhook/自托管渠道无 SSRF 防护（CWE-918）

- **定位**：`src/adapters/webhook.mjs:10-30`、`src/adapters/_shared.mjs:76-99` —— 直接 fetch，无私网段拦截，无 `redirect:'manual'`；响应片段（≤2048 字符）进错误对象形成探测回显
- **易错辨析**：URL 仅 admin token 持有者/YAML 编辑者可控，定级因此压在中危——但 token 被钓后即成内网跳板，且回显通道让 SSRF 从盲打变明打。易错点：`redirect:'manual'` 的缺失意味着重定向可绕过任何未来加的 URL 校验
- **竞品参照**：dsh-im 无自定义 webhook 渠道，无此面；但其 API 客户端统一 `redirect:'error'`（`telegram-api.mjs:357-363`、`dingtalk-api.mjs:207-213`），重定向显式拒绝有先例可循

### S-03 · 中危 · answer+parallel 审批模式：IM 账号凭据即可放行高危审批（能力设计的安全代价）

- **定位**：`src/approval/router.mjs:68,499-523`、`src/inbound/bus.mjs:231-299` —— answer+parallel 模式下 IM 账号被盗 = 可远程放行 bash 沙箱升级类审批；竞态路径 `ledger.resolve()` 不检查前态
- **易错辨析**：已有缓解厚实（observe 默认、token 单次核销+SHA-256+常量时间比较、来源会话校验、A2 轮专项确认裁决链无 TOCTOU），但 parallel 模式把"设备在身边"的假设换成"IM 账号在手"——安全边界从物理降级到口令。辨析点：这不是实现漏洞而是能力设计的安全代价，审视时应关注高危审批是否该有第二因子
- **竞品参照**：竞品无审批远程裁决面，最小能力反而无此险

### S-04 · 中危 · 各渠道凭证明文落盘 state.json（CWE-312）

- **定位**：`src/inbound/store.mjs:262-276`、`src/admin/api.mjs:910-913`、`src/admin/scan.mjs:187-203`
- **易错辨析**：缓解已到位（0600+原子写+跨进程锁；admin token 例外仅存 hash；GET 全 mask），剩余风险是文件系统级读取（同用户进程、备份同步、误提交）。辨析：D3 轮确认企微 `corpsecret` 走 URL query 是官方 API 固有形态（POST 不可用），日志侧 `_shared` 错误对象不含 URL——"secret 进 URL"的暴露面在协议本身而非实现，与竞品一致
- **竞品参照**：dsh-im 同样明文 JSON 落盘，无 keychain 集成

### S-05 · 中危 · 自动通知默认外发宿主会话数据片段（CWE-200）

- **定位**：`src/event-listener.mjs:16-37,295-309,389`、`src/approval/router.mjs:242-243` —— 输出片段 200 字符/workspace 名/session id/错误全文发往第三方 IM；notify 工具允许 LLM 推任意字符串
- **易错辨析**：默认行为即外发，用户无感知确认；prompt injection 可借 notify 工具构造外发通道。缓解（500 字符上限、工具限流、出站不触发命令）降低可利用性但数据流向本身未告知。辨析：这与"通知插件"的产品本质绑定，审视重点应是默认片段的敏感度而非有无外发
- **竞品参照**：dsh-im 是双向桥,默认即转发会话内容,外发面更大

### S-06 · 中危 · 管理台无 CORS/Origin/CSRF 策略（CWE-352/942）

- **定位**：`src/admin/server.mjs` 全文无 Origin 处理

- **竞品参照**：dsh-im 无 HTTP 管理面

### S-07 · 中危 · ask_user 远程回答注入 agent 上下文（CWE-74）
