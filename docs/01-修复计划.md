## W1 钉钉 Stream 协议修正

Branch `codex/fix-dingtalk-stream-protocol`。清 G-01、G-02（P1）与 G-10、G-23、G-24、G-42（P2/P3），全部同文件同协议面。

Owned files：`src/inbound/dingtalk-stream.mjs`、`test/inbound.dingtalk.test.mjs`、`docs/protocol-preflight/dingtalk.md`（新建）、`CHANGELOG.md`。

**G-01 ack 回执三重偏差**（`src/inbound/dingtalk-stream.mjs:219-227` 调用点 `:307`）

当前 `ackFrame(String(frame.messageId))` 读顶层 messageId、回执头用 `requestId` 字段名、`data:'ack'` 未字符串化。官方 SDK 三版源码一致确认正确形态为：messageId 取自 `frame.headers.messageId`；回执头字段名就是 `messageId`；`data` 是 JSON 字符串 `"OK"`。改法：

```js
function ackFrame(messageId) {
  if (messageId === '') return
  sendFrame({
    code: 200,
    headers: { contentType: 'application/json', messageId },
    data: JSON.stringify('OK'),
  })
}
// 调用点：ackFrame(String(frame.headers?.messageId ?? ''))
```

**G-02 SYSTEM/ping 零应答**（`:303-316` `handleFrame` 无 SYSTEM 分支）

增加分支：`frame.type === 'SYSTEM'` 且 `headers.method/event_type` 判定为 ping 时，原样回显 `sendFrame({ code: 200, headers: frame.headers, data: frame.data })`（data 含必须回显的 opaque）；disconnect/KEEPALIVE/REGISTERED 记 debug 日志后返回，不进业务路径。注意与传输层 WS 心跳是两码事，不得合并处理。

**G-10 建连字段名**（`:201`）

`uesrAgent: 'dsh-notifier'` 改为 `ua: 'dsh-notifier'`，删除“官方 SDK 的拼写错误字段名，照抄勿改”注释——该说法经三版 SDK 源码核对查无实据（全系 `ua: this.config.ua`）。新注释注明核对结论与版本号，防再犯。

**G-42 data 二次 parse 失败静默**（`:311-313`）

parse 失败从静默 return 改为：warn 日志（含 messageId、frame.type、内容前 64 字符）后仍 return。ack 已发则服务端不重推，丢消息至少要可观测；同时在 `docs/memory/risks.md` 记录“ack 先于解析”的取舍。

**G-23 richText 未归一**

richText 回调遍历内容模块：text 段拼接进 envelope.text，图片模块走既有 picture/image 管线；纯文本/纯图行为不变。

**G-24 被动回复 messageId 合成碰撞**（`:433-439`）

hash6 合成改为 `reply-${Date.now().toString(36)}-${(++seq).toString(36)}`（模块级单调 seq），同会话同内容两次回复不再同 ID。

Focused tests（重写 `test/inbound.dingtalk.test.mjs` mock 形态，当前 mock 把错误契约钉死成测试基线，是 G-01 漏检直接原因）：

1. 服务端帧 messageId 仅存在于 `headers.messageId`，顶层无该字段，断言 ack 仍发出且头字段为 `messageId`、`data === '"OK"'`。
2. SYSTEM/ping 帧（headers 含 method:'ping'、data 含 opaque）→ 断言回显帧 headers/data 等值；SYSTEM disconnect → 断言不进业务分发。
3. data 非法 JSON → 断言 warn 被调用且不投递。
4. 被动回复两次同内容 → messageId 不同。
5. richText 混排（text+image）→ 文本与图片分别入信封。

真机门（记 `docs/memory/risks.md`，不阻塞合入）：真实钉钉机器人 Stream 连接挂 10 分钟，验证 ping 周期不再断连、消息不再被服务端 60s 重推。新建 `docs/protocol-preflight/dingtalk.md` 沉淀协议证据（对齐 telegram/feishu 等既有预检文档格式）。

/** 按 Unicode 码点切块：绝不产生孤立代理项（emoji/生僻字跨块安全）。 */
export function splitByCodePoints(text, size) {
  const chars = Array.from(String(text ?? ''))

- 修复是否只对“确定性失败”重试，对“结果未知”投递停手（W6 之后新写适配器同样受此约束）？
- 公开错误文案（事件、工具反馈、admin UI、按钮回执）里是否还残留响应体片段、HTTP 原文、底层 message、机器路径？
- 协议类修复的仲裁源引用是否写进了代码注释或 protocol-preflight 文档（防止下一个人把 `ua` 又改回 `uesrAgent` 类悲剧重演）？
- mock 变更是否与实现同源共生（改实现不改 mock 形状 = 白改）？fixtures 是否来自 SDK 源码/官方文档而非手想？
- 破坏性语义变化（/stop 更严、错误文案换码、去重窗口缩短）是否在 CHANGELOG 顶部显著标注迁移说明？
- 定时器/监听器/inflight 新增的每一处是否都有 dispose/clear 路径（C1+D1 轮清点基线不得回退）？
- 真机缺口是否记入 `docs/memory/risks.md`，发布说明是否避免了“已验证”措辞？
